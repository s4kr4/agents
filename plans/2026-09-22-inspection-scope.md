# 実験: 想定入力範囲を計画段階で宣言し、検証のブロック判定をその範囲に限定する

- 作成日: 2026-09-22
- 状態: **実験中（導入済み。効果は次の代表的なタスクで測る）**
- 根拠: `~/.agents/CLAUDE.md` の「エージェント構成の見直し方針」

## 背景

検証フェーズ（`@code-safety-inspector`）の不合格が「新しい敵対的入力の軸」を1周ごとに1つずつ見つける形で続き、イテレーション上限に達する。

- 2026-09-15 の実験（`plans/2026-09-15-implementer-opus.md`、implementer を sonnet から opus へ）では、計測期間中のイテレーション上限到達がゼロになった。ただし交絡4点（タスクの性質・作業の刻み方・継続作業による範囲の絞り込み・inspector の判定範囲の部分適用）により、改善をモデル差に帰属できなかった
- その後 2026-09-17〜22 に実施した `scripts/check-skill-sync.sh` の修正では、スキルへのフィードバック反映（23件）を済ませた状態でも **4イテレーション**を要した。不合格の内訳は、(1) 元からあった短絡、(2) 修正がパス族を区別しない、(3) ステージされた側を起点にした片方向検証 で、いずれも「直した条件の隣」からの再発だった
- この4イテレーションの間、実装担当の誤りは1件もなく、毎回テスト全通過・shellcheck 警告ゼロだった。不合格は実装の精度ではなく、想定する入力の範囲と判定の不変条件を決める役目が実質 Phase 4 にしかないことに起因する

## 仮説と判断

- 再発の共通構造は「判定の基準が状況依存で定義されていたこと」である。基準は 未コミット差分の有無 → mode/oid の一致 → パス族 → ステージの向き と、指摘のたびに条件を足す形で移り変わった
- 最終的に「両側がそれぞれの正規形にある」という状況に依存しない基準へ変えた時点で収束した。状況依存の基準は、状況を1つ足すたびに穴が1つ開くため、指摘と修正が1対1で対応し続ける
- したがって、**計画段階で不変条件を1文で宣言させ、検証のブロック判定をその範囲に限定する**。軸の正本は `/tdd` の「🎯 想定入力範囲の軸」（既に導入済み）とし、宣言の形式は `@code-planner`、範囲の判定は `@code-safety-inspector`、フェーズ間の規定は `development-workflow.md` に置く
- 変数は「想定入力範囲の宣言と判定範囲の限定」の1つのみ。`plans/2026-09-15-implementer-opus.md` の「判定 > 次の実験候補 (b)」にあたる

## 評価基準

普段の代表的なタスク2〜3件を、想定入力範囲を宣言した構成で実施する。

| 観点 | 計測方法 | 期待 |
|---|---|---|
| イテレーション上限到達 | 上限に達したタスク数 | 0 |
| 同じ原因の別軸での再不合格 | 前回と同じ根本原因が別の軸で再検出された件数 | 0 |
| 範囲内の塞ぎ漏れ | 宣言した集合・不変条件の内側で再不合格になった件数 | 0。>0 なら宣言の粒度が不足 |
| 範囲外の所見 | 件数と、うち「範囲外・重大」の件数 | 所見は出る（0 なら範囲が広すぎて従来と同じ）。重大は少数 |
| 範囲改訂 | Phase 2 への差し戻し回数 | 1タスク1回以内 |
| 見逃し | コミット後に発覚した不具合の件数と、宣言範囲の内外 | 0。範囲内で発覚したら設計の失敗 |
| 宣言の空文化 | inspector が「範囲の内外を判定できなかった」と報告した件数 | 0 |
| 宣言コスト | 計画承認の往復回数 | 増加なし |

## 判定

- 上限到達0かつ範囲内の塞ぎ漏れ0かつコミット後の範囲内不具合0 → 採用する
- 上限到達が再発 → 宣言の粒度（集合で書けているか・不変条件が1文になっているか）を先に確認する
- 上限到達0だが「範囲外・重大」が多い → 範囲が狭すぎる。軸の選択基準を改訂する
- 範囲内の塞ぎ漏れ>0 → `code-planner.md` の Step 4.6 の書き方の基準を改訂する
