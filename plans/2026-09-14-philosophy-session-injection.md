# 作業方針（philosophy）のセッション自動注入

- 作成日: 2026-09-14
- 状態: 検証イテレーション3まで完了（2026-09-15）。フック本体（`memory/hook-session-start-philosophy.sh`）・`--require-vault`・Claude Code 側の登録（`.claude/settings.json`）・テスト・文書はいずれも実装済みで、未コミットの変更をコミットする段階

## 背景

ユーザーの作業方針（設計哲学）には専用の置き場が無く、`CLAUDE.md`・rules・共有メモリの各所に分散していた。共有メモリへの読み出しも「大きな作業の開始時に検討する」という運用上の推奨に留まり、セッション開始時に確実に読み込ませる強制力がなかった。

## 判断

- **正本は共有メモリ**とする。「プロジェクトを越える思想は共有メモリに置く」というユーザーの方針に基づき、`philosophy` タグ付きの記憶（global scope、10件）を正本にし、`CLAUDE.md`/`AGENTS.md` 側には参照の仕組みだけを書く
- **フックと指示文書を併用する**。セッション開始時の注入は SessionStart フックで機械的に行えるが、設計判断の時点（実装アプローチの選択・トレードオフの検討など）はフックで検知できないため、`CLAUDE.md`/`AGENTS.md` に「設計判断では注入された方針を根拠として示す」旨の指示を併記する
- **Codex の起動ラッパー方式（`codex-memory-run.sh` 相当）は採らない**。ラッパーはセッション開始時の1回しか注入できず、`/compact` 相当の圧縮後に方針が失われても再注入できないため、SessionStart フック（`compact` にもマッチ）を採用する
- **Codex 側の定義はユーザーが `~/.codex/hooks.json` に手動追記する**。ユーザーの決定。既存の `~/.codex/hooks.json` に herdr 関連の既存フックが登録済みで、リポジトリ側から機械的に統合すると既存定義を壊すリスクがあるため
- **matcher から `resume` と `fork` を外し、`^(startup|clear|compact)$` とする**。resume/fork は元の会話に注入済みの philosophy コンテキストがそのまま残っているため、再注入すると重複する
- **注入上限は Codex の制約を基準にする**。Codex の SessionStart 注入は既定で概ね 2,500 トークン程度が上限とされているため、全体 2,000 字・1 件 300 字に抑えた。Claude Code 側の実効上限（一部情報源にある 10,000 字目安）は未確認のため、Codex 側の狭い制約に合わせて安全側に倒した
- **`memory.py` に `--require-vault` を追加する**。Vault 未設定時に local 側などへ静かにフォールバックすると、フックが「0件」として何も注入しないまま正常終了してしまい、設定不備に気付けない。明示的にエラーにして検知できるようにする
- **失敗時（Vault 未設定・Python 不在・timeout 等）は exit 0 のまま注意文を注入する**。フックの失敗でセッション開始自体を止めたくない一方、注入が無かったことを気付かせるため、「shared-memory の search（scope=global, tags=["philosophy"]）で取得すること」という注意文を `additionalContext` に載せる
- **要件が曖昧な場合の方針を Codex 側の記述に揃えた**。`.codex/AGENTS.md` に既にあった「作業範囲を変えない合理的な仮定を優先し、必要なときだけ確認する」という記述に `.claude/CLAUDE.md` 側を合わせ、両クライアントで判断基準を一致させた
- **注入する各行に記憶の id を `[id]` 形式で併記する**。MCP の `write_memory` はどのセッションからでも global scope に `philosophy` タグを付けられるため、信頼できない内容に誘導されたエージェントが作った記憶が、以後のすべてのセッションに方針として注入されうる（永続するプロンプトインジェクションの経路）。ユーザーは書き込みの制限は行わず、id を併記して不審な項目に気付けるようにする対策を選んだ
- **`search` は上流で件数を絞らず全件を対象にし、id 昇順の先頭から採用する**。件数がフックの文字数上限を超える場合のみ末尾側を省略し「ほか N 件」と明示する。上流の `--limit` で黙って取りこぼす経路を残さないため
- **`LLM_MEMORY_HOOK_TIMEOUT` は 1〜8 の整数のみ有効とする**。範囲外・非整数の値は既定の5秒にフォールバックする。Claude Code 側の hook timeout（10秒）より必ず短くし、外側のタイムアウトで打ち切られて CLI のプロセスが孤児化するのを防ぐため
- **macOS 対応として、時間制限コマンドは `timeout` を優先し、無ければ `gtimeout`（Homebrew coreutils）を使う**。どちらも無ければ注意文を注入する。jq は両 OS で必須依存とし、macOS では `brew install jq coreutils` を前提とする。macOS 標準の bash 3.2 でも動く書き方にする（実機での確認は未実施）
- **`BASH_ENV` 等、起動時に stdout・stderr へ出力するシェル設定はスクリプト内では防げないため、前提条件として文書に明記するに留める**。あわせてネイティブ Windows にはこのフックを配布しない（配布は bash 版 `deploy.sh` のみで、PowerShell 版の導入スクリプトは MCP のみを扱うため）
- **`--require-vault` のエラー文は CLI 専用の `--vault` フラグに触れず、`LLM_MEMORY_VAULT` と config.toml を案内する**。同じ文言が MCP サーバー経由でも出るため
- **id・summary の偽装対策は、記憶ごと除外せず「summary はそのまま活かし、行・id の偽装だけを塞ぐ」形にする**。ユーザーが選んだのは、summary の改行と ASCII の制御文字（U+0000〜U+001F、U+007F）を空白に置き換えて1行化し、id に `[`・`]`・空白・制御文字を含む記憶は注入対象から除外する方式（Unicode の行区切りが対象外である点は N5 参照）。検討した他の選択肢は (a) 該当記憶を丸ごと除外する案、(b) 危険な文字をエスケープして見せる案で、いずれも中身を無駄に落とす／見た目が崩れるためユーザーは採らなかった
- **summary が空または空白のみの記憶も除外する**。これはオーケストレーターが置いた仮定であり、ユーザーの明示決定ではない

## 検証（イテレーション1）で見つかった問題

- `search` に付けていた上流の `--limit` により、philosophy タグの記憶が上限を超えると黙って取りこぼされていた
- `mktemp` の失敗パスが stderr にエラーメッセージを漏らしていた（フックは stderr を出さない契約に反する）
- jq 自体が失敗した場合に何も出力されず、無出力のまま exit 0 していた（注意文を出すべきケースを見逃していた）
- `--require-vault` の効果や jq/timeout 不在時のフォールバックなど、主要なガードに対する回帰テストが不足していた

## 検証（イテレーション2）で見つかった問題

- N1: イテレーション1の修正で全件を受け取るようにしたところ、本文の組み立てが件数に対して二乗を超えて遅くなり、3,000件で92秒かかって時間切れになった。組み立て処理は `LLM_MEMORY_HOOK_TIMEOUT` の外側にあり、jq プロセスが孤児として残ったまま無出力で終わっていた
- N2: summary 内の改行や `]` を使うと、別の記憶の id を名乗る行を偽造できた
- N3: 応答の型が不正でもエラーにならない値（`memories` が `null` など）が素通りし、無出力のまま exit 0 していた
- N4: 先頭の1件も本文に入らない（0件注入になる）経路がテストされていなかった

## 検証（イテレーション3）で見つかった問題

- イテレーション2の指摘（N1〜N4）はすべて解消を確認した。性能は10,000件で1.58秒、独立変異試験23種でテストギャップは0件だった
- N5（残存、既知の問題として記録）: summary に含まれる Unicode の行区切り（U+0085、U+2028、U+2029）が空白へ置き換えられず、そのまま注入される。これらを使うと行や見出しの偽造ができる。id 側の空白・角括弧の判定は jq の `\s` が Unicode に対応しているため U+2028 等も拒否できているが、summary 側の置換対象が ASCII の制御文字のみで、id 側と summary 側で判定基準が非対称だったことが原因
- ユーザーの判断: この時点でコミットし、N5 の修正（`replace_controls` の置換対象に U+0085・U+2028・U+2029 を追加する。既存テストが期待する U+0080 の扱いは変えない）は別作業とする
