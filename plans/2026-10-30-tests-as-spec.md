# テストを仕様書として読める形にし、RED の仮実装をやめる（ドキュメント・複数ファイル）

## Context

目指す状態は「テストケースが仕様書の代わりになる」こと。開発の手法は問わないが、テストは必ず人間が読める形で残す。

現状の問題は次の3つ。

- **仕様の置き場所が散らばっている**: 完了条件は計画、受け渡しの内容は委譲プロンプトと tester レポート（どちらも会話の中で揮発する）、振る舞いはテストにある。テストの名前は言語によって英語の関数名（Python）と日本語の文（シェル）が混在し、ハーネスのコードの間に埋もれて仕様として通読できない
- **実装を三重に書いている**: tester が充足可能性チェックのために動く仮実装を書いて捨て、implementer が同じものを書き、inspector が変異試験でもう一度確かめる。記録上、仮実装は実質的に本番の実装と同じもので、テストが通せるかの確認を一括の受け渡しで遅らせた分の埋め合わせになっている
- **手順書が実態と食い違っている**: `tdd/SKILL.md:142` は「1サイクルで書くのは最小単位のテスト1つ」と書いているが、オーケストレーション時は一括で書いて渡している

ユーザーの決定:

- テスト名（仕様文）は**日本語**で書く（他人と共有するプロジェクトに既存の規約があればそちらを優先）
- tester の仮実装は**やめる**。tester / implementer の分離は維持する（philosophy「作り手と検証者を分ける」）

## 目標の形

### 情報の置き場所

| 情報 | 置き場所 | 残り方 |
| --- | --- | --- |
| 何がどう振る舞うか | テスト（日本語の仕様文。ケースの存在理由は仕様の補足コメント） | git に残る。正本 |
| なぜそうするか・範囲・除外 | `plans/` の計画（完了条件・想定入力範囲） | git に残る |
| 工程の受け渡し（件数・ログ・変異試験の結果） | エージェントのレポート | 揮発してよい |

将来の読み手が必要とする情報を、レポートだけに書かない。

### フロー（変更点のみ）

- **Phase 1（計画）**: 完了条件を、そのままテストの仕様文になる1文ずつの形で書く
- **RED（tester）**: 完了条件ごとに、仕様文を名前に持つテストを書く。仮実装は書かない。代わりに、実装が無くてもできる**ハーネスの自己検査**（スタブが絞り込んだ PATH で起動できる・環境変数がテスト対象まで届く・テストごとの作業領域が独立している・収集件数が0件でない）を行う。変異試験は開始時 GREEN のアサーション（既存コードが対象）に限る。レポートには、テストランナーの一覧出力から作る**仕様一覧**と、完了条件との対応表を載せる
- **GREEN（implementer）**: テストを仕様として読み、計画の完了条件と照らし合わせる。完了条件に無い振る舞いを求めるテスト（偽の要件の疑い）や、アサーション以外の理由（スタブの起動失敗など）で落ちるテストは、実装を合わせずに差し戻す
- **検証（inspector）**: behavior アサーションへの変異試験（現行どおり）に加え、**仕様としての可読性**を確かめる。対応するテストが無い完了条件はブロック、名前とアサーションの乖離・ハーネスに埋もれた構成は警告

## 範囲外

- **既存テストの書き換え**: 日本語の仕様文への移行は、今後テストに触れるときに順次行う。一括では移行しない
- **`scripts/test_*.py` 等の冒頭コメント**「（充足可能性チェック・変異試験用）」: コードのファイルのコメントであり、8ファイルに及ぶため別の変更として扱う
- **受け渡しの経路**（レポートをファイル経由にする等）: 今回は置き場所の原則だけを定め、経路は変えない

## 試行の評価（philosophy「プロセスは仮説として扱い、実験で見直す」）

仮実装の削除は削減にあたるため、確定前に試行する。手順書には新しい構成だけを書き、試行の記録はこの計画に置く。

- **対象**: この変更の後の、テストを伴う代表的なタスク2〜3件
- **比べる指標**: tester ⇔ implementer の差し戻し回数のうちハーネス・期待値の欠陥によるもの、inspector の不合格のうちテスト側の欠陥によるもの、RED フェーズの所要
- **戻す条件**: ハーネスや期待値の欠陥が GREEN 以降まで素通りし、手戻りが仮実装のコストを上回った場合。戻す先は手順 0 のコミット

## 検証（ドキュメント分類の完了確認）

- **参照整合性**: `grep -rn "充足可能性" .claude .codex --exclude-dir=feedback` の残りが、範囲外とした `scripts/` のコメントだけであることを確かめる。改名した節「📝 仕様として読めるテスト」・「ハーネス自身の検査」を指す参照が実在の節に一致することを確かめる
- **移設の完全性**: 削除する節から残す内容（一時変更の手順・Write/Edit の規約・環境変数の設計）を、編集前後の `diff` で失われていないことを示す
- **ミラー同期**: ステージした状態で `scripts/check-skill-sync.sh` が exit 0 になることを確かめる
