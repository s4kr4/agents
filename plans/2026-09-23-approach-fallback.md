# 実験: 同一根本原因での再不合格を検出したら、実装修正ではなくアプローチへ差し戻す

- 作成日: 2026-09-23
- 状態: **実験中（導入済み。効果は次の代表的なタスクで測る）**
- 根拠: `~/.agents/CLAUDE.md` の「エージェント構成の見直し方針」

## 背景

検証フェーズ（`@code-safety-inspector`）の不合格が「同じ根本原因の別軸」として1周ごとに1つずつ再発し、イテレーション上限（3回）に達する。記録上の3件:

- herdr タブバーのレートリミット表示（2026-09-09）: 先頭ゼロの8進数解釈によるバイパス → 同じ原因のロケール軸（`[!0-9]` の照合順序）と続いた
- philosophy 注入フック（2026-09-14〜15）: 件数の欠落 → 区切り文字による偽造 → Unicode の行区切り（U+2028 等）による偽造で上限到達
- `make update` を検査する bash ハーネスの起動前ガード（2026-09-22、`.claude/skills/tdd/feedback/2026-09-22-8.md`）: イテレーション1で `-n` を迂回する6経路、イテレーション3で**申告外の8経路**（`ifeq` ブロック内のタブ字下げ、一行レシピ `target: ; +cmd`、`$(shell` の継続行による分断、変数連結による `.RECIPEPREFIX` の構成）が実測され上限到達

3件に共通する点:

- **実装担当の誤りは0件**。毎回の指摘も、それに対する修正も正しい。テストは全通過し、静的解析の警告もゼロだった
- `plans/2026-09-15-implementer-opus.md` の実験（implementer を sonnet から opus へ）でも構造は変わらなかった。同記録の「判定」に「当初の見立て（主因はプロセス設計）は否定されていない」「『想定する入力の軸を見つける役目が検証フェーズにしかない』構造は変わっていない」とある
- 2026-09-22 の件で正しい解だったのは実装修正ではなく**アプローチの変更**だった。grep で危険構文を列挙するブラックリストは、Make の文法が変数展開で名前を組み立てられる以上、原理的に網羅できない。列挙をやめて封じ込め（危険が実を結ばない環境で実行する）へ形式を変えるべきだった

現行ルールでは、フィードバックループの出口が「実装を直す」しかない。Phase 2 へ戻る経路は「想定入力範囲の改訂」だけで、その発火条件は inspector が「範囲外・重大」を報告した場合に限られる。上記3件はすべて**範囲内**での不合格のため、この経路は一度も発火しない。

## 仮説と判断

- フィードバックループの収束性は「発見の生成率」と「修正の処理率」の比で決まる。inspector 側には「迷ったら不合格」「範囲の内外に迷えば範囲内としてブロック」「diff 全体をフルスコープで再検査」「変異試験で新しい変異を自分で設計できる」が積み上がっている一方、implementer 側は「最小実装で1軸ずつ」である。到着率が処理率を上回れば、双方が正しく仕事をしていても待ち行列は発散する
- さらに、指摘が正しくても**防御の形式が列挙型（ブラックリスト・状況依存の条件分岐）である限り、1周1軸のペースは変わらない**。条件を1つ足すたびに穴が1つ開くため、指摘と修正が1対1で対応し続ける。イテレーション上限を引き上げても収束点は移らない
- したがって、**同一根本原因での再発を検出したら実装修正のループを打ち切り、設計（防御の形式）の変更へ差し戻す**経路を新設する。検出は inspector に根本原因の分類（新規か、前回と同じ原因の別軸か）を書かせることで行い、差し戻し先は `@code-planner` とする
- 変数は「アプローチ差し戻し経路の新設」の1つのみ。イテレーション上限の値・分類やパターンの表・`@tester`／`@implementer` の定義は変更しない

## 評価基準

普段の代表的なタスク2〜3件を、アプローチ差し戻し経路を含む構成で実施する。

| 観点 | 計測方法 | 期待 |
|---|---|---|
| イテレーション上限到達 | 上限に達したタスク数 | 0 |
| アプローチ差し戻しの発火 | 発火回数と、発火後に合格するまでの検証イテレーション数 | 発火は出てよい。発火後は1〜2回で収束 |
| 分類の記載率 | inspector の不合格レポートで、各指摘に根本原因の分類（新規／前回と同じ原因の別軸）が記載された率 | 100% |
| 誤発火 | 別の根本原因なのに「同じ原因」と分類され、差し戻しになった件数 | 0 |
| 差し戻し後の再発 | アプローチを変えた後、同じ根本原因で再び不合格になった件数 | 0 |

## 判定

- 上限到達0かつ差し戻し後の再発0 → 採用する
- 上限到達が再発 → 分類の粒度（根本原因の同一性をどう判定しているか）を先に確認する。「別軸」を「新規の原因」と分類していれば検出が働かない
- 誤発火>0 → 分類基準を改訂する。差し戻しのコストは計画フェーズの往復であり、誤発火は素の実装修正より高くつく

## 交絡の管理

- implementer は opus のまま固定する。`plans/2026-09-15-implementer-opus.md` の実験とは変数が別である
- `plans/2026-09-22-inspection-scope.md`（想定入力範囲の宣言と判定範囲の限定）が**評価データ未取得のまま並走する**。2026-09-22 に上限到達した案件には想定入力範囲の宣言自体が無く、同実験の効果は未計測である。したがって本記録の計測期間には2つの導入済み変更が同時に効いており、改善をどちらに帰属させるかは、発火した経路（範囲改訂かアプローチ差し戻しか）の記録で切り分ける
- 未処理のスキルフィードバックの反映を同時に行わない

## 除外範囲

- 分類・パターン・フェーズ選択ガイドの表の変更
- `@tester`・`@implementer` のエージェント定義の変更
- イテレーション上限（3回）の値そのものの変更
- `/tdd` の軸表への「構文位置の軸」の追加（別課題として `.claude/skills/tdd/feedback/2026-09-22-8.md` に未処理で残す）
