# 実験: implementer のモデルを sonnet から opus へ

- 作成日: 2026-09-15
- 状態: **実験実施済み（2026-09-16）。opus を維持。ただしモデル差の寄与は未確定（交絡あり）**
- 根拠: `~/.agents/CLAUDE.md` の「エージェント構成の見直し方針」

## 背景

検証フェーズ（`@code-safety-inspector`）の不合格が続き、イテレーション上限（3回）に達するタスクが多い。記録上の2件:

- herdr タブバーのレートリミット表示（2026-09-09）: 検証1回目で先頭ゼロの8進数解釈による鮮度ガードのバイパス、2回目で同じ原因のロケール軸（`[!0-9]` の照合順序）が不合格。3回目の結果は記録なし（`.claude/skills/tdd/feedback/processed/2026-09-09-4.md`〜`-9.md`）
- philosophy 注入フック（2026-09-14〜15）: 1回目で上流 `--limit` による件数の欠落など、2回目で修正起因の性能劣化・型の素通り・区切り文字による偽造、3回目で Unicode の行区切り（U+2028 等）による偽造が不合格となり、上限に到達（`.claude/skills/tdd/feedback/2026-09-14-4.md`・`-7.md`・`2026-09-15-1.md`）

## 仮説と判断

- 不合格が「指示（プロセス設計）」と「モデルの精度」のどちらに起因するかを切り分けるための実験。変数は implementer のモデルのみ（1つずつ変える）
- sonnet だったのは implementer だけで、tester・code-planner・code-safety-inspector は opus。見逃された入力の軸は opus の tester・planner も見逃していたため、事前の見立ては「モデル差の寄与は小さく、主因はプロセス設計」。この実験はその見立ての反証を試みるもの
- 見立てで主因と考えている点（この実験では変更しない）: 想定する敵対的入力の範囲を計画段階で決めていない／inspector のブロック判定に範囲の上限がない／GREEN の「最小実装」と「同じ原因の入力空間の網羅」が衝突する

## 評価基準

普段の代表的なタスク2〜3件を現行ワークフローで実施し、上記2件と比較する。

| 観点 | 計測方法 |
|---|---|
| 検証イテレーション数 | 合格までの回数、上限到達の有無 |
| 修正起因の新規問題 | 前回指摘の修正が別の問題を生んだ件数（例: 2026-09-14 の N1） |
| 同じ原因の別軸での再不合格 | 前回と同じ根本原因が別の軸で再検出された件数 |
| 実装ミス | implementer のスキルフィードバック申告のうち、言語・DSL の書き間違い（例: jq の構文誤り）の件数 |

## 交絡

1変数の実験として設計したが、次の4点が同時に変わっていたため、改善をモデル差に帰属できない。

1. タスクの性質: 変更前の2件は bash + jq による敵対的な文字列解析（8進数解釈・ロケール・Unicode 行区切り）だったが、今回は改名・移動・パス解決が中心で、落とし穴の密度が低い
2. 作業の刻み方: 「複雑」分類の切り出し作業を M1〜M6 + M-a に分割し、各段階を個別に検証した。1回の検証で見る範囲が小さくなれば指摘は収束しやすい。これはモデルとは無関係なプロセス側の変化
3. 最初の1件（N5 修正）は、上限到達した指摘そのものを直す継続作業で、範囲が最初から絞られていた
4. inspector の判定範囲: 1件目（N5 修正）では、inspector への依頼でブロック対象を「差分が持ち込んだ不具合と N5 の塞ぎ漏れ」に限定し、それ以外を範囲外の所見として分けさせていた（「## 評価データ > 1件目」参照）。これは「## 判定 > 次の実験候補 (b)」に挙げた指示側の変更にあたり、実験期間中に部分的に適用されていた。実際に範囲外の所見が1件出ているため、範囲を限定しなければ不合格になっていた可能性がある

## 判定

- イテレーション数・修正起因の問題が明確に減った → モデル差の寄与ありとして opus を確定し、`implementer.md` はそのまま、本記録の状態を更新する
- 変化がない → `model: sonnet` へ戻し、プロセス設計側の改善（計画段階での入力範囲の決定、inspector の判定範囲の限定）を次の実験にする
- タスクの言語・難度が上記2件（どちらも bash + jq）と大きく異なる場合は比較上の注意として記録する

実際の判定:

- opus を維持する（実装ミス0件で悪化の証拠がないため）。ただし「モデル差が主因だった」とは結論できない
- 当初の見立て（主因はプロセス設計）は否定されていない。不合格2件はいずれもテスト側の穴であり、「想定する入力の軸を見つける役目が検証フェーズにしかない」構造は変わっていない
- 次の実験候補（いずれも1変数）:
  - (a) `@code-planner` の成果物に「独立に検証できる段階への分割」を求める（今回の交絡2が効いた可能性が高く、コストがかからない）
  - (b) 計画段階で入力の想定範囲を決め、`@code-safety-inspector` のブロック判定をその範囲に絞る
    - 1件目（N5 修正）で部分的に適用済みであり、次はタスク全体に適用して効果を測る
