# 敵対的検証（Adversarial Testing）

テストが「通ること」ではなく「壊したときに落ちること」を担保するための指針です。敵対的入力空間の設計軸、隔離が空振りを生まないための設計、変異試験によるテストの検出力の検証を定義します。

## 責務

- 完了条件・テスト・変異の設計で使う入力空間の軸を選び、各軸で許容する集合を宣言する
- 各入力を到達経路と影響度で採否判定し、対応しない入力を範囲の外に置く
- 隔離（環境変数の遮断・依存の制限・モック）が検証したい失敗そのものを発生不可能にしていないかを確認する
- テスト対象自身が破壊的な副作用を持つ場合に、実環境を壊さないための 3 重防御を適用する
- 変異試験でテストの検出力を直接確認し、生存した変異をテストギャップ / 範囲外のテストギャップ / 等価変異 / 冗長被覆に分類する

## 境界

- このスキルが扱うのは「入力空間の設計」と「防御が効いていることの検証」に限る
- TDD のサイクル（Red-Green-Refactor）、RED の種別、tester / implementer のオーケストレーション手順は `/tdd` を使う
- 言語・用途別のテスト記法やフレームワーク設定は `/api-test`、`/ui-test`、`/py-implement`、`/ts-implement`、`/sh-implement` を使う

## 🎯 想定入力範囲の軸

完了条件で敵対的入力空間を列挙するときに使う軸表。対象に関係する軸を選び、各軸で**許容する集合**を宣言する。`@tester` は入力空間の設計に、`@code-safety-inspector` は変異の設計に使う。代表的な値は集合を考えるための例であり、すべてを検証対象にする指示ではない。検証対象にするかどうかは「採否の基準」で決める。

| 軸 | 見るもの | 代表的な値 |
|----|---------|-----------|
| **表記** | 同じ値の別表記 | 先頭ゼロ（8 進解釈）・符号・基数プレフィックス・小数・前後の空白・CRLF |
| **文字集合** | 同じ意味を持つ別のコードポイント | Unicode 行区切り（U+0085 / U+2028 / U+2029）・双方向制御（U+202E）・ゼロ幅（U+200B / U+FEFF）・非 ASCII 空白（U+3000 / NBSP）・全角数字 |
| **型** | エラーにならずに素通りする不正値 | null・false・キー欠落・空配列・型違い |
| **量** | 件数・サイズと処理時間の関係 | 桁違いの件数、外側のタイムアウトとの関係、上流での件数打ち切りと下流の並び替え・集計の不整合 |
| **出力の区切り** | 出力が構造を持つ場合の区切り文字の混入による偽造 | 改行・括弧・区切り文字を含む入力 |
| **上流との契約** | 依存先の出力の変化 | 出力形式の変更・`ok:false`・欠損キー・部分的な失敗・一時ファイル作成の失敗 |
| **実行環境** | 環境依存の挙動 | ロケール（照合順序・文字クラス）・PATH・タイムゾーン・依存コマンドの有無 |
| **構文位置** | 静的検査・正規表現ガードで、同じ意味の構造が別の位置に書けること | アンカー（`^`・行頭・行末）の前提と対象言語の文法の不一致、一行レシピ `target: ; cmd`、継続行、ブロック内のインデント、変数連結による名前の構成 |
| **型宣言** | 型定義が検証対象のときに崩れうる箇所 | 名前・引数型・戻り値型（同期と Promise）・`any` への崩れ |

- 軸は**集合**として宣言する。「改行を拒否する」ではなく「行区切りとして解釈されうるコードポイント全体（LF / CR / U+0085 / U+2028 / U+2029）を拒否する」と書く。代表値の列挙だけで宣言すると、同じ意味を持つ別の文字・別の表記が視野の外に出て、検証フェーズで 1 軸ずつ順に不合格になる
- 外部仕様が定める集合（OS の予約名・不正文字・プロトコルの予約語など）は、既存の実装の列挙を正本にせず、一次資料から列挙する。上付き・全角・互換文字などの変種が正規化の後に残るかも確かめる（例: Windows の予約名には `COM¹`〜`COM³` が含まれる）
- 正規化・変換を挟んでから判定する設計では、許容集合と拒否集合のそれぞれが変換の前と後のどちらの値に対する判定かを明記する。変換で無害な形に変わる拒否値（`nul.txt` は slug 化で `nul-txt` になる）は、変換前の判定が要る。テストでは「拒否値 × 正規化で除去される成分（前後の空白・タブ・大文字小文字）」の組み合わせを拒否の入力に含める
- テストの入力では、問題の文字・バイトを判定に効く位置（値の先頭・途中）にも置く。行末のコメントなど判定に関わらない位置だけに置くと、照合の穴を検出できない
- 構文位置の軸で、対象の文法が動的（変数展開で名前を組み立てられる等）で列挙が原理的に網羅できない場合は、ブラックリストではなく封じ込め（危険が実を結ばない環境で実行する）を選べないか検討する
- 設定値・環境変数を読むコードのテストでは、既定値（フォールバック）と観測上区別できる値（別のホスト・解決できないホスト名など）を与える。既定値と同じ結果になる値では、読み取りが壊れていても通る
- 同じ入力に対する許可・禁止の判定が実装内の複数箇所にある場合、判定基準（文字集合）を 1 箇所に集約するか、双方が同じ集合を見ていることを確認する。判定基準の非対称が塞ぎ漏れになる
- 制御文字・NUL・双方向制御文字は、テストのソースにリテラルで埋め込まず `chr(0)` などの式で生成する。言語によってはソースに含められず、テストモジュール自体がパースに失敗する。書き込み後に生の文字が混入していないことを走査して確認する

### 採否の基準

軸と集合を選んだら、各入力を**到達経路**と**影響度**で判定し、対応するかどうかを決める。対応しない入力は計画の「想定しない条件」に判定理由とともに記載し、テスト・実装・ブロック判定の対象から外す。

- **到達経路**: その入力を実際の運用で「誰が・どの操作で」生成するかを名指しする。例: ユーザーの通常操作、手編集されたファイル、別 OS・別マシン由来のファイル、依存コマンドが実際に出す出力形式、過去に観測された不具合。発生頻度の見積もりではなく経路の有無で判定する。頻度は推測でしか書けないが、経路は生成元を示して確かめられるため
- **影響度**: 起きたときの失敗の重さ。**重大**はサイレントな不正値受理・データ破損・信頼境界を越える権限の取得・秘密情報の露出。**限定的**はエラー終了など目に見える失敗で、入力を直して再実行すれば回復するもの。どちらか迷う場合は重大として扱う

| 到達経路 | 影響が重大 | 影響が限定的 |
|----------|-----------|-------------|
| 通常の運用で来る | 対応する | 対応する |
| まれだが名指しできる | 対応する | 対応する |
| 名指しできない | 信頼境界の外から来る入力なら対応する | 対応しない |

- 経路を名指しできなくても、信頼境界の外から来る入力で影響が重大なら対応する。攻撃者の入力は自然に発生する頻度に従わないため
- 同じ根本原因が別の軸で再現する場合も、その軸の入力に同じ基準を当てる。基準を満たさない軸は塞ぎ漏れとして扱わない
- 「想定しない条件」に書く除外理由（「影響が限定的」「許可の方向に倒れない」など）は事実の主張である。計画の段階で実測して確かめるか、検証フェーズで確かめる項目として明記する。理由が事実として誤っていた場合、その除外は無効であり、採否の基準で判定し直す（計画側は想定入力範囲の改訂として扱う）

## 🔒 隔離テスト環境の設計指針

環境変数を空にする・利用できる依存（実行パス・コマンド・権限）を絞る・依存をモックへ差し替える、といった隔離は副作用防止に有効だが、**検証したい失敗そのものを発生不可能にする**ことがある。隔離を設計するときは「隔離が防御として働き、バグを構造的に隠していないか」を確認する。

- **副作用の非発生を検証するケースでは、副作用を起こす手段を隔離で取り除かない**。副作用に必要な依存（コマンド・権限・書き込み先）を環境から外したまま「副作用が起きないこと」を検証すると、実装が抑止しているのではなく失敗できないだけの空振りになる。実行環境に近い状態で走らせる
- **環境（ロケール・探索パス・タイムゾーン等）に依存する挙動は、その環境を明示的に複数パターン与えるテストを別途用意する**。環境を空にする隔離は、環境依存そのものを修正するコードの検証で特に危険である。テスト環境が修正後と同じ状態を常に再現してしまい、未修正でもテストが通るため。「環境を与えないと全 pass する」ことを変異で確認する
- **対象がロケールを固定していない場合は、テスト環境に実際の利用者のロケール（例: `LANG=ja_JP.UTF-8`）を 1 パターン含める**。環境を空にする隔離は C ロケールで動くため、UTF-8 ロケールでだけ起きる不具合が見えない
- **異常系・破損系テストの既定アサーションに「stderr が空であること」を含める**。stdout しか見ないと、stderr にだけ現れる副作用（実行時の警告等）を取り逃す
- 前提条件（特定のロケール・依存コマンドの可用性）の判定は「名前の存在確認」ではなく**実際の挙動の probe** で行う。名前はあるが挙動が異なる環境で黙って空振りするため

### 破壊的スクリプトをテスト対象にする場合

デプロイ・インストール・マイグレーション・クリーンアップなど、**スクリプト自身が破壊的な副作用**（ファイルの作成・削除・リネーム、設定の書き換え）を持つ場合は、テストの失敗が実環境の破壊に直結する。以下の 3 重防御をテストコードに含める:

1. **環境の遮断**: 環境変数を継承させず、ホームディレクトリ等の基準パスを明示的に stub へ差し替える
2. **起動前ガード**: stub パスが一時ディレクトリ配下であること、実環境のパスと一致しないこと、互いに配下関係がないことを検証し、違反時はアサーションではなく `exit` で即座に中断する（テストの継続自体が危険なため）
3. **事後スナップショット比較**: 実環境の該当箇所を実行前後で比較し、変化していないことをアサーションとして書く

対象スクリプトが対象パスを環境変数で受け取れる設計なら、ダミーのツリーを作って実リポジトリにも触れずに済む。テスタビリティの観点から「パスをハードコードせず環境変数で受ける」設計を推奨する。

## 🧪 変異試験（テストの実効性検証）

「全テスト pass」は品質の証拠にならない。テストが実装に追随して空振りしている、入力空間に穴がある、という状態でも pass 件数は同じである。変異試験でテストの検出力を直接確認する。

### 手順

1. 主要なガード（入力検証・境界判定・エラー処理・副作用の抑止）を**1 つずつ意図的に外した実装**を用意する
2. 各変異に対してテストを実行し、**対応するテストが落ちること**を確認する
3. 変異体は baseline と同一の環境で実行し、**実行件数と skip 件数が baseline と一致すること**を確認してから生存・kill を判定する。テストが SKIP されると変異は必ず生存するため、隔離した実行環境（PATH の最小化など）が生存の原因になっていないかを先に潰す
4. 変異を当てたら、外したガードの先の経路が実際に実行されたこと（ログ・呼び出し記録）を確かめてから判定する
5. 原本と同一内容の複製に対する control 実行は、差し替え機構（環境変数フック等）が効いていることの検証にはならない。差し替え先だけを壊すカナリア（`exit 1` → `exit 7` 等）で機構自体を確認する
6. 落ちない（生存した）変異は、「生存変異の分類」に従って分類し、レポートに記載する

### 生存変異の分類

| 分類 | 条件 | 記載すること |
|------|------|-------------|
| テストギャップ | 想定入力範囲の内側に、変異を区別しうる入力がある | 区別しうる入力と、追加すべきテスト |
| 範囲外のテストギャップ | 区別しうる入力はあるが、想定入力範囲の外側にしかない | 区別しうる入力・範囲外である根拠（「想定しない条件」の該当項目、または到達経路を名指しできない理由）・範囲に加える場合に必要なテスト |
| 等価変異 | 区別しうる入力が無い | 立証に使った入力集合と比較の結果 |
| 冗長被覆 | 対象テストでは生存し、スイート全体では別のテストが kill する | kill したテスト名 |

- **範囲外のテストギャップ**は、検証フェーズの「範囲外の所見」と同じ扱いにする（ブロックしない。コミット確認時にユーザーへ提示する）
- **等価変異の立証責任**: 生存した変異がすべてテストギャップとは限らないが、等価変異の主張には立証責任がある。**その変異を区別しうる入力を特定した上で**、原本と変異版を同一入力で実行し、終了コード・stdout・stderr を直接比較して一致を示す。区別しうる入力が特定できない場合は、等価ではなくテストギャップとして扱う
  - 区別しうる入力は集合として列挙する（例: バイト値 0x01〜0xFF × 値の位置 × 起動時のロケール）。実行件数と不一致の件数を報告する
  - 同じ入力集合で、複数の生存変異をまとめて立証してよい
- **冗長被覆の確認**: 生存したら、まずテスト選択を広げて（クラス全体・ファイル全体）再実行する。対象テストクラス単独では生存し、スイート全体では別のテストが kill する（冗長被覆）ケースがある
  - 宣言した想定入力範囲が特定の呼び出し箇所（特定のリンク・特定の設定キー）に紐づくときは、共通ヘルパー経由の被覆を冗長被覆とみなさない。呼び出し箇所の不変条件を、宣言軸の各集合で直接確かめる

### 実施タイミング

- **RED（tester）**: 開始時 GREEN のアサーション（退行ガード・invariant guard・否定形）の有効性の根拠として必須。behavior の failing アサーションについても、充足可能性チェックの仮実装に変異を当てて検出力を確認する。RED では複製を作らず本来のパスで変異させ、`/tdd` の充足可能性チェックと同じ手順で戻す
- **Phase 3（safety inspector）**: 独立した視点で実施する。tester が見落とした入力空間はここで見つかることが多い

### パターン

- **網羅性の証明**: 検証したい副作用を無条件に発生させる変異（例: スクリプト冒頭で stderr へ出力）を当て、失敗件数と起動回数の一致を確認する。「stderr 未検証の起動がゼロ」をアサーションの付け漏れなしに機械的に示せる
- **対称ガードの片側**: `a <= 上限` と `b <= 上限` のような対称なガードは、片側だけ回帰保護が抜けやすい。テスト内の値の分布（片方に `101` があるのにもう片方は `100` まで）を確認する
- **重ねた防御**: 同じ値を複数の防御で守る場合（終了コードの確認と空チェックなど）、通常の失敗入力では、防御を 1 つずつ外す変異が互いに補い合って生き残る。各防御について、他の防御だけを素通りする入力を用意する（例: 失敗時に値を出力して非 0 で終わるスタブ、空を出力して 0 で終わるスタブ）

### 注意

- **正規化の直後に当てた変異**: 正規化処理（例: `str(Path(...))`）の直後に当てた変異は観測差が消えやすい。この場合は変異の当て方を正規化の前へずらしてから判定する
- **観測差の判断材料**: 既存テストの入力だけで観測差の有無を判断しない。別の入力値・ロケール・環境でプローブする
- **ファイル変更禁止との整合**: 検査中にプロダクションコードを変更できない場合は、スクラッチパッドへ一式を複製し、複製側で変異させる。ハーネスは対象パスを相対解決か環境変数で受ける設計にしておく
  - ハーネスが自身の位置（`__file__` / `BASH_SOURCE`）からツリー構造を解決する場合は、対象コードだけでなく**テストファイル自身も複製先へコピー**し、複製側のツリーで実行する
  - 複製はテストが必要とするファイル（ソース・設定・ロックファイル）に限る。ローカルストア・DB などの実データを複製に持ち込まない
  - Python プロジェクトの例: 対象ディレクトリのソースとロックファイルだけを複製し、原本の環境から `uv run --project <原本>` で複製側のテストを実行する
  - 依存の解決（`node_modules`・仮想環境）は複製せず、原本へのシンボリックリンクにするか原本の環境から実行する。テストが対象を固定の相対 import で読む場合も、テストファイルと対象を一緒に複製すれば複製側で実行できる
  - それでも複製側で実行できない場合、検証フェーズ（inspector）は原本を変更せず、実行できなかった変異とその理由を報告する
  - 作業ディレクトリとログの出力先は、起動前に絶対パスへ解決する。途中で `cd` したあと相対パスで書き出すと、原本リポジトリに未追跡ファイルを作る
  - 複製ハーネスを作ったら、変異を当てずに**ベースラインが GREEN であること**を先に確認する。その後、1 変異ごとに「当てて fail」「戻して GREEN」を対にして確認する
  - 複製先はセッション内で一意な新規ディレクトリ名にする。スクラッチパッドは同一セッションの他エージェントと共有されるため、既存ディレクトリへ重ねて展開しない
  - **`rm` はスクラッチパッド配下でも一切使えない**（`permissions.deny` の対象）。後始末だけでなく作業ディレクトリの作り直しも対象。不要になったものは `.discarded` へのリネームで無効化し、新しい作業は毎回一意な名前で新規に作る
  - 対象が環境変数でパスや依存を差し替えられる設計なら、複製せずフック経由で変異版を指してもよい。複製より軽く、ハーネスと対象の対応が崩れない
