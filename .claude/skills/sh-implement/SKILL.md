# Shell Script Implementation Best Practices

シェルスクリプト（bash）実装のベストプラクティス、落とし穴、テスト規約です。既存スタイルの踏襲だけでは決まらない判断の既定値として活用してください。

## 📐 適用範囲

- **スクリプトファイル**（`#!/bin/bash`）: 全体を適用する
- **スクリプトファイル以外に埋め込まれたシェル片**（Makefile のレシピ、CI の run ブロック、`package.json` の scripts）: 「シェル固有の落とし穴」を適用する。ファイル単位の基準（`set -euo pipefail`・冒頭の契約コメント・`LC_ALL=C` の固定）は適用しない
  - Makefile のレシピは行ごとに別のシェルで起動される。変数や `set` は次の行へ引き継がれない
  - `make -n` は実行しないことを保証しない。行頭が `+` の行・`$(MAKE)` を含む行・`$(shell)` / `!=` / `$(file)` の展開は実行される
- **source される設定ファイル**（rc の断片）: 「迷ったときの既定」の該当行を参照する

## 🎯 Core Principles（コア原則）

### 1. **Safety over Style**（安全性を既存スタイルより優先）
- 安全性と既存スタイルが競合した場合の優先順位は `/tdd` の「スキル指定表」直下の注記に従う
- シェルでは特に、既存スクリプトに前例がない安全な書き方（`LC_ALL=C` の固定・入力検証の前置）を採用してよい。理由をレポートに明記する

### 2. **Deterministic Evaluation**（決定的な評価）
- 数値判定・文字数計算・正規表現や文字クラスによる照合を行うスクリプトは冒頭で `LC_ALL=C` を固定する。UTF-8 ロケールでは、不正なバイト列を含む行が grep にバイナリとして扱われたり、`\S` などの文字クラスに当たらなかったりして、照合から漏れる
- 同じ値でも評価する構文によって結果が変わる（「シェル固有の落とし穴」参照）
- 入力検証は数値演算より前に置く

### 3. **Explicit Failure Policy**（失敗時の方針を明示）
- `set -euo pipefail` は定石だが万能ではない。スクリプトの性質ごとに方針を選ぶ
- 冒頭のコメントで契約（読み出し専用・常に exit 0 など）を宣言し、実装をそれに従わせる

### 4. **Portability**（移植性）
- 外部コマンドへの依存を減らすほど、最小 PATH でも動く
- GNU / BSD で非互換なオプションを避け、bash 組み込みで代替できるものは組み込みを使う

## ⚠️ シェル固有の落とし穴

いずれも `shellcheck` は検出しない（0.9.0 で 8 項目を実測。出力ゼロ・exit 0）。

| 落とし穴 | 何が起きるか | 対処 |
| -------- | ------------ | ---- |
| **先頭ゼロの算術** | `$(( ))` は先頭ゼロを 8 進解釈し `08` でエラーになる。`[ ]` は基数 10 で受理する。同じ値でも構文で結果が違う | 入力検証で先頭ゼロを弾く。10 進を明示するなら `$((10#$v))` |
| **算術エラー後の継続** | 算術エラーが起きるとそのリスト全体が破棄され、`[ "$((...))" -le N ] \|\| exit 0` の `\|\| exit 0` が発火しないまま次の行へ進む | ガードを独立した文にし、検証を数値演算より前に置く |
| **巨大数** | `[ "$v" -le N ]` は 64bit を超えると stderr へ `integer expression expected` を出して exit 2。`$(( ))` は黙って折り返す（`2^63` が負値になる） | 桁数チェックを数値比較の前に置く |
| **ロケールと文字クラス** | `case` の `[0-9]` は照合順序で解決され、`en_US.UTF-8` では全角 `０` を数字として受理する。`[[:digit:]]` は POSIX で ASCII 固定のためこの問題はないが、`${#var}` がバイト数か文字数かは依然ロケール依存 | 冒頭で `LC_ALL=C` を固定して両方をまとめて決定的にする。理由をコメントに残す |
| **リダイレクトの評価順** | 左から右へ評価されるため、`cmd > f 2>/dev/null` では `> f` 自体の失敗を隠せない | まとめて抑止するなら `{ cmd > f; } 2>/dev/null` で包む |
| **`stat` の非互換** | `stat -c`（GNU）と `stat -f`（BSD）は非互換で、移植先で黙って失敗する | エポック取得は bash 組み込みの `printf '%(%s)T' -1`（4.2 以降）を使う |
| **`shopt -p` の終了コード** | 指定したオプションのどれかが off だと非 0 を返す（出力自体は正しい）。`set -e` の下で `x="$(shopt -p dotglob nullglob)"` と状態を保存するとそこで止まる | 変更をサブシェル `( shopt -s dotglob nullglob; ... )` に閉じ込め、保存・復元をしない |
| **コマンド置換と NUL** | `$(…)` は NUL を保持できず、落としたうえで stderr に `warning: command substitution: ignored null byte in input` を出す（bash 5.2 で実測） | NUL が意味を持たないなら `{ x=$(…); } 2>/dev/null` で警告を抑える。意味を持つならファイルかパイプで受け渡す |

算術エラーの実例は、必ず複数行の形で確認する。`;` で 1 行に並べた形では再現しない。

```bash
now=1757400000
updated_at=08
[ "$((now - updated_at))" -le 900 ] || exit 0
printf 'reached\n'        # ← 到達する。ガードが飛ばされている
```

### bash から呼ぶ DSL（jq・awk 等）

- プログラムは埋め込む前に単体で実行して確かめる（`jq -n '<program>'`）。DSL のエラーは bash 側では空出力や後段の失敗として現れ、原因を特定しにくい
- DSL の終了コードを確かめ、空出力を成功とみなさない
- 正規表現の文字クラスを書いたら、一致すべき値と一致してはならない値の両方で実測する。方言の差はエラーではなく誤判定として静かに現れる（例: jq の Oniguruma では、文字クラス内の `\u0000-\u001f` が範囲として働かず `"g"` にも一致する。`\x00-\x1f` を使う）

## 🚦 エラー処理の方針

| スクリプトの性質 | 方針 |
| ---------------- | ---- |
| 本番の処理系（デプロイ・同期・チェック） | `set -euo pipefail` |
| 失敗しても出力を続けるもの（statusLine・タブバー表示） | `set` を使わず、処理ごとに個別のガードを置き**常に `exit 0`** |
| テストハーネス | `set -uo pipefail`。失敗ケースの実行自体が目的なので `-e` は付けない |

## 🔧 迷ったときの既定

| 論点 | 既定 |
| ---- | ---- |
| 引数を条件付きで組み立てる | 配列を使う（`#!/bin/bash` なら利用可）。スペース区切りの文字列で代用しない |
| 条件式 | bash 前提なら `[[ ]]`。`sh` 互換が必要な箇所だけ `[ ]` |
| 外部コマンド | 起動回数を減らす。最小 PATH で動く必要があるものは組み込みだけで書く |
| パスの受け取り | ハードコードせず環境変数で受け、既定値を `${VAR:-...}` で与える。テスト時に差し替えられる |
| 変数名 | 小文字スネークケース。環境変数として公開するものだけ大文字 |
| 引数解析 | `-h` / `--help` は usage を **stdout** に出して exit 0。不明な引数は stderr にメッセージと usage を出して exit 1（黙って無視しない）。フラグは加算ではなく代入で扱い、重複指定を冪等にする |
| source される設定ファイル | 旧定義が残ったシェルで再 source しても同じ結果になるようにする。alias を関数に置き換えるときは先に旧 alias を除去する（alias は関数より先に展開されるため、残ると修正が効かずエラーも出ない）。テストには旧定義を入れた状態から source するケースを置く |

## 🧪 テスト

テストの設計方針は `/tdd` に従う。隔離の設計は `/adversarial-testing` の「🔒 隔離テスト環境の設計指針」、破壊的スクリプトは同節の 3 重防御を参照する。ここではシェルでの実現方法だけを挙げる。

- テストは、対象と同じ種類（同じディレクトリ・同じ役割）の既存テストの形式に倣う。プロジェクト内で形式が分かれている場合は対象に最も近い既存テストを基準にし、選んだ理由をレポートに記す
- 別言語のハーネス（Python の subprocess 等）から起動する場合は、環境を `env=` で明示して継承させず、`timeout=` を必ず指定する（孫プロセスがパイプを握ったままだと `communicate()` が戻らない）。タイムアウトの検証では孫プロセスを残すスタブを使い、プロセスツリー全体が止まることを確かめる
- 環境の遮断は `env -i` で行い、ホームディレクトリ等の基準パスは stub を明示的に渡す
- ハーネスは自分の位置を `BASH_SOURCE` から解決し、テスト対象へは対象パスを環境変数で渡す
- **ロケール依存の検証は `LC_ALL` を明示的に複数パターン渡す**。`env -i` はロケールを常に C にするため、渡さなければ全 pass して空振りする
- 前提ロケールの判定は `locale -a` の名前検索ではなく、実際に `case` を走らせる probe で行う
- 異常系・破損系では stdout と stderr を別々の一時ファイルへ捕捉し（`> "$out_file" 2> "$err_file"`）、読み込んだ **stderr が宣言した契約どおりであること**を assert する。エラーを stderr へ出さない契約なら空文字列であること、出す契約なら非空かつ期待する内容であることを検証する。契約に無い stderr 出力（実行時の警告など）は副作用として検出したいので、stderr に何も assert しない形は避ける
- 依存コマンドの不在は、`/usr/bin`・`/bin` の写しから対象だけを除いたディレクトリを PATH にして作る。テスト用の bin を外すだけではシステム側の同名コマンドが見える。不在になっていることを `command -v` でハーネス自身が確かめる
- 否定形の存在チェックは `[ ! -e p ] && [ ! -L p ]` と書く。`-e` はリンクをたどるため、壊れたリンクを見逃す
- エージェントのシェルは bash とは限らない（zsh 等）。zsh には `PIPESTATUS` が無く、クォートしない変数も単語分割されない。テストの起動・変異の生成・検査のコマンド列はファイルに書き出して `bash` で実行し、終了コードは直後の `$?` で取る

## ✅ Quality Standards（品質基準）

実装したコードは以下の基準を満たす必要があります：

- ✅ `shellcheck` の警告ゼロ（対象は既定の重大度 = style 以上すべて）
  - 誤検知は、該当行に限定した `# shellcheck disable=SCxxxx` と、なぜ誤検知かを述べた理由コメントを添えて抑止してよい。ファイル冒頭での一括抑止は行わない
  - テストハーネスでは SC2317（`trap` や間接呼び出しされる関数を unreachable と判定する）が系統的な誤検知として出る
  - 誤検知かどうか判断がつかない場合は抑止せず、レポートで報告する
  - 基準は新規に書く部分に適用する。既存ファイルに倣った結果として同種の指摘が出るのは許容する（`project-conformity.md` が優先）
- ✅ 数値・文字列長・正規表現の照合を扱うなら `LC_ALL=C` を固定、または固定しない理由が明確
- ✅ 入力検証が数値演算より前にある
- ✅ 失敗時の方針（`set` の有無・終了コード）が冒頭の契約と一致している
- ✅ 意図が自明でない行（環境依存の回避・順序に意味がある処理・一見無関係に見える設定行）に理由コメントがある
- ✅ GNU 固有のオプションに依存していない
- ✅ 外部コマンドの起動回数が必要最小限

## 🔍 Code Review Checklist（コードレビューチェックリスト）

コード実装後、以下を確認してください：

- [ ] `shellcheck` を実行し、警告がない（抑止している場合は行限定で理由コメントがある）
- [ ] 数値入力に対し、先頭ゼロ・非 ASCII の数字・巨大数・空白を検証している
- [ ] 算術展開より前に入力検証のガードがある
- [ ] `|| exit` に依存したガードが、算術エラーで飛ばされない形になっている
- [ ] リダイレクトのエラー抑止が意図した範囲に掛かっている
- [ ] `set` の方針がスクリプトの性質と一致している
- [ ] 条件付きの引数組み立てに配列を使っている
- [ ] テストが実環境へ書き込まない（`env -i` と stub パス）
- [ ] ロケール依存の挙動に、複数ロケールのテストがある
