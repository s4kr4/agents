# TDD（テスト駆動開発）ガイドライン

テスト駆動開発（TDD）の原則、手順、ベストプラクティスを定義します。具体的なコード例やフレームワーク設定は `/api-test` `/ui-test` `/ts-implement` `/py-implement` 等の言語/用途別スキルを参照してください。

## ⛔ 適用範囲の早期判定

読み込んだら、まずタスクに対してこのスキルのどこまでが適用対象かを判定する:

- **テストで検証できる実装（Web API / UI / CLI / スクリプト / ライブラリ）**: スキル全体が対象。「🎭 オーケストレーション手順」（tester / implementer 分離）に従う。ドメインによる差はエージェントではなく委譲時に指定するスキルで吸収する
- **RED 種別の判定**: タスクが「型・設定・非推奨 API の移行（ランタイム挙動が変わらない）」または「既存挙動を維持する純粋なリファクタリング」に該当するかを確認し、該当する場合は「🧭 RED の種別」に従って behavior 以外の RED を選択する。この判定を怠ると、後続フェーズ全体が「failing テスト必須」という誤った前提で進む
- **軽微変更（同パターン6）**: スタイル値・文言・コメントのみの変更でテスト作成自体を行わないため、スキル全体が対象外。この時点で以降を読み飛ばしてよい

詳細は `~/.claude/rules/development-workflow.md` の「フェーズ選択ガイド」「Phase 3」を参照。

## 🎭 オーケストレーション手順

このスキルが起動されたら、以下の手順を**毎回必ず実行**する。

### 手順

1. 承認済み計画からスコープを確認（API / UI / CLI・スクリプト・ライブラリ）
2. `@tester` に委譲:
   - 入力: **フェーズの明示（Phase 3a / RED）**、**RED 種別の判定結果（「🧭 RED の種別」参照）**、**参照するドメイン固有スキル**（「スキル指定表」参照）、完了条件（振る舞い記述）、対象ファイル、既存パターン
   - 完了条件には以下を明示する:
     - **数値仕様の丸め規則と境界値**（切り捨て / 四捨五入、上下限の内外）。例示値は丸め規則が判別できる値（割り切れない値・`.5` 境界）を選ぶ
     - **敵対的入力空間の列挙**。数値入力なら先頭ゼロ・符号・基数プレフィックス・空白・CRLF・オーバーフロー・ロケール（全角数字等）まで含める
     - テスト対象自身が破壊的な副作用を持つ場合は「🔒 隔離テスト環境の設計指針」の 3 重防御を要求する
   - 委譲プロンプトに「実データに書き込まない」制約と、環境変数で保存先が決まる場合の明示上書きを含める
3. tester からのレポートを受領:
   - テストファイル一覧
   - テストケース一覧
   - **RED 種別**（behavior / static diagnostic / characterization baseline / invariant guard）と**種別ごとの件数**（failing の実装対象 / passing の退行ガード・否定条件 / invariant guard を分離して報告する）
   - 種別に応じた失敗根拠:
     - behavior: 実装対象アサーションが全件 failing の実行ログ
     - static diagnostic: 対象診断（compiler / lint / deprecation）の検出ログ
     - characterization baseline / invariant guard: 開始時 GREEN の実行ログと、変異試験で fail することの確認結果
   - **充足可能性チェック**の結果（「🔧 Red-Green-Refactor 詳解」手順 3）
   - **変異試験**の結果（「🧪 変異試験」）。生存した変異はテストギャップと等価変異を区別して記載
   - 前提条件を満たせず SKIP したケースの件数と理由
4. レポートを添えて `@implementer` に委譲:
   - 入力: **フェーズの明示（Phase 3b / GREEN）**、tester レポート、承認済み計画のスコープ、**参照するドメイン固有スキル**（「スキル指定表」参照）
   - 検証フェーズ不合格を受けた再入場の場合は、指摘レポートと追加された回帰テストも入力に含める（「🔧 Red-Green-Refactor 詳解」の「フィードバックループでの再入場」参照）
5. implementer から「GREEN 達成」レポートを受領
6. 後続フェーズ（UI 検証 or safety inspector）へ。safety inspector への委譲プロンプトには「🧪 変異試験」の実施を含める

### スキル指定表

委譲プロンプトで指定するドメイン固有スキル。

| スコープ | tester に指定 | implementer に指定 |
|---------|--------------|-------------------|
| バックエンド API | `/api-test` | `/ts-implement` または `/py-implement` |
| フロントエンド UI | `/ui-test` | `/ts-implement`, `/react-implement` |
| CLI / スクリプト / ライブラリ | 言語に応じて `/py-implement` / `/ts-implement` のテスト規約。シェルは `/sh-implement` | 言語に応じて `/py-implement` / `/ts-implement`。シェルは `/sh-implement` |

既存スタイルの踏襲を基本とするが、誤りが不具合や脆弱性に直結する側面（入力の検証・エラー処理・実行環境前提の固定〈ロケール・探索パス・タイムゾーン等〉・外部から受け取る値の扱い等）で既存スタイルと競合する場合は**安全性を優先**し、採用理由をレポートに明記する。それ以外の様式（命名・整形・構成）は既存スタイルに従う。シェルスクリプトの落とし穴・検証手段は `/sh-implement` を参照する。

API + UI 両方を含む場合は API 側を先に完結してから UI 側へ進む。

多層変更（ストア → CLI → MCP など）は承認済み計画のタスク単位で RED → GREEN を繰り返してよい。ただし各タスク内でも tester が先に failing テストを作り、implementer はテストを編集しない。

### 差し戻しルール

implementer が「テスト自体が不正（要件誤解・セットアップ不備）」と判断した場合:

- implementer は**自分でテストを修正しない**
- オーケストレーター経由で tester に差し戻し、理由を伝える
- 差し戻しは**同一テストにつき最大 2 回**まで
- 3 回目はユーザーにエスカレーション

## 🎯 TDDの基本原則

### Red-Green-Refactor サイクル

TDDは以下の3ステップを繰り返すサイクルで進めます：

**🔴 RED: 失敗するテストを書く**

- テストファイルを作成/編集する
- 期待する振る舞いをテストとして記述する
- テストを実行して失敗を確認する（意図した assertion での失敗であること）

**🟢 GREEN: テストを通す最小限のコードを書く**

- テストを通すことだけに集中する
- 完璧なコードを書こうとしない

**🔵 REFACTOR: リファクタリング**

- テストが通る状態を維持しながら改善する
- 重複の除去・可読性向上・既存パターンとの一貫性を維持する
- テストが通ることを再確認する

### TDDの3つの法則

1. **失敗するテストを書くまで、プロダクションコードを書いてはならない**
2. **失敗するテストを必要以上に書いてはならない**（コンパイルエラーも失敗とみなす）
3. **現在失敗しているテストを通すために必要なプロダクションコード以上を書いてはならない**

## 🧭 RED の種別

RED は「失敗する振る舞いテスト」に限らない。種別は**タスク単位ではなくアサーション単位**で決まり、1 つの RED フェーズに複数種別が同居してよい。tester レポートには種別ごとの件数を明記する。

| 種別 | 対象 | RED の定義 | GREEN の定義 |
|------|------|-----------|-------------|
| **behavior**（既定） | 新規仕様の実装・実挙動が変わるバグ修正 | 期待する振る舞いを記述したテストが failing | テストが passing |
| **static diagnostic** | 型・設定・非推奨 API の移行（ランタイム挙動が変わらない） | compiler エラー / lint エラー / deprecation 診断（例: TS6385）が検出されている状態 | 対象診断がゼロになり、既存テストが GREEN を維持 |
| **characterization baseline** | 既存挙動を維持する純粋なリファクタリング | （failing を要求しない）現行挙動を固定する characterization test が**開始時から GREEN であることが正常** | リファクタリング後も baseline テストが GREEN を維持 |
| **invariant guard** | 現行実装が既に満たしている不変条件・ガードの固定（変異試験で未テストと判明したガードへの回帰保護など） | （failing を要求しない）開始時 GREEN が正常。**対象ガードを外した変異で fail すること**が有効性の根拠 | 実装変更後も GREEN を維持 |

- 「全ケース failing」の確認は **behavior RED の実装対象アサーションにのみ適用**する。以下は behavior RED に同居していても開始時 GREEN が正常であり、failing を要求しない:
  - ガード条件の否定形（「条件を満たさない場合は呼ばれない」「失敗しても exit 0」等。未実装状態でも構造的に通過する）
  - 既存挙動の退行ガード（characterization 相当）
  - invariant guard
- 開始時 GREEN のアサーション（characterization baseline / invariant guard / 否定形）は、**対象を壊した変異で fail することを確認してから完了**とする（「🧪 変異試験」参照）。確認できないテストは回帰保護として機能していない
- ランタイム挙動が変わらない変更に対して無理に failing テストを作ろうとすると、実装詳細テストや偽の要件を生む（アンチパターン）
- リファクタリングや移行の途中で実際の不具合を発見した場合は、**その不具合だけを behavior RED として追加**する（例: characterization は GREEN のまま、境界条件の実不具合のみ failing テスト化）

## 📋 TDD実装手順

### 1. 要件の分解

機能を小さなテストケースに分解します。チェックリスト形式で列挙し、粒度は「1ケース = 1つの振る舞い」を目安とする。

### 2. テストの優先順位

シンプルなものから着手する:

1. 正常系の最も基本的なケース
2. 境界値のケース
3. エラーケース

### 3. AAA パターン（Arrange-Act-Assert）

各テストを以下の3段構成で記述する。コメントで明示するとテストの意図が伝わりやすい。

- **Arrange（準備）**: テスト対象・入力データ・モックの用意
- **Act（実行）**: 対象メソッドの呼び出し
- **Assert（検証）**: 結果の期待値比較

## 🎨 テスト設計パターン

### テストダブルの種類

| 種類     | 用途                     | 使いどころ                                  |
| -------- | ------------------------ | ------------------------------------------- |
| **Stub** | 固定値を返す             | 依存先の返り値を固定したいとき              |
| **Mock** | 呼び出しを検証           | 依存先が正しく呼ばれたか確認したいとき      |
| **Spy**  | 実際の実装を呼びつつ監視 | 本物の挙動を保ちつつ呼び出し記録を残したい  |
| **Fake** | 簡易版の実装             | インメモリDBなど本物の代替で統合的に試したい |

### フィクスチャ

テストデータ生成は **ファクトリ関数 / fixture** を用意し、`overrides` で個別ケースの差分だけを記述する。テスト間でデータを使い回す場合でも依存関係を生まないよう毎回新しいインスタンスを返すこと。

仕様が「保持」「順序」「範囲」「冪等性」を保証する場合、fixture には**実装が想定する正規形から外れた入力**を必ず含める（手編集されたファイル、CRLF、タイムゾーンの異なる日時、境界値の外側など）。正規形の入力だけで構成された fixture は実装者の前提をなぞるだけで、独立した検証にならない。比較の粒度も保証に合わせる（バイト保持なら `read_bytes()` 同士で比較する）。

### モック利用の指針

- 外部 I/O（DB / HTTP / ファイルシステム）は原則モック
- ただしモックが多すぎると統合面の不具合を見逃すため、結合テストでバランスを取る
- プロダクションコード側の実装詳細（private メソッド呼び出し等）は検証しない

## 🔒 隔離テスト環境の設計指針

環境変数を空にする・利用できる依存（実行パス・コマンド・権限）を絞る・依存をモックへ差し替える、といった隔離は副作用防止に有効だが、**検証したい失敗そのものを発生不可能にする**ことがある。隔離を設計するときは「隔離が防御として働き、バグを構造的に隠していないか」を確認する。

- **副作用の非発生を検証するケースでは、副作用を起こす手段を隔離で取り除かない**。副作用に必要な依存（コマンド・権限・書き込み先）を環境から外したまま「副作用が起きないこと」を検証すると、実装が抑止しているのではなく失敗できないだけの空振りになる。実行環境に近い状態で走らせる
- **環境（ロケール・探索パス・タイムゾーン等）に依存する挙動は、その環境を明示的に複数パターン与えるテストを別途用意する**。環境を空にする隔離は、環境依存そのものを修正するコードの検証で特に危険である。テスト環境が修正後と同じ状態を常に再現してしまい、未修正でもテストが通るため。「環境を与えないと全 pass する」ことを変異で確認する
- **異常系・破損系テストの既定アサーションに「stderr が空であること」を含める**。stdout しか見ないと、stderr にだけ現れる副作用（実行時の警告等）を取り逃す
- 前提条件（特定のロケール・依存コマンドの可用性）の判定は「名前の存在確認」ではなく**実際の挙動の probe** で行う。名前はあるが挙動が異なる環境で黙って空振りするため

### 破壊的スクリプトをテスト対象にする場合

デプロイ・インストール・マイグレーション・クリーンアップなど、**スクリプト自身が破壊的な副作用**（ファイルの作成・削除・リネーム、設定の書き換え）を持つ場合は、テストの失敗が実環境の破壊に直結する。以下の 3 重防御をテストコードに含める:

1. **環境の遮断**: 環境変数を継承させず、ホームディレクトリ等の基準パスを明示的に stub へ差し替える
2. **起動前ガード**: stub パスが一時ディレクトリ配下であること、実環境のパスと一致しないこと、互いに配下関係がないことを検証し、違反時はアサーションではなく `exit` で即座に中断する（テストの継続自体が危険なため）
3. **事後スナップショット比較**: 実環境の該当箇所を実行前後で比較し、変化していないことをアサーションとして書く

対象スクリプトが対象パスを環境変数で受け取れる設計なら、ダミーのツリーを作って実リポジトリにも触れずに済む。テスタビリティの観点から「パスをハードコードせず環境変数で受ける」設計を推奨する。

## 🧪 変異試験（テストの実効性検証）

「全テスト pass」は品質の証拠にならない。テストが実装に追随して空振りしている、入力空間に穴がある、という状態でも pass 件数は同じである。変異試験でテストの検出力を直接確認する。

### 手順

1. 主要なガード（入力検証・境界判定・エラー処理・副作用の抑止）を**1 つずつ意図的に外した実装**を用意する
2. 各変異に対してテストを実行し、**対応するテストが落ちること**を確認する
3. 落ちない（生存した）変異は、テストギャップか等価変異かを判定してレポートに記載する

### 実施タイミング

- **RED（tester）**: 開始時 GREEN のアサーション（退行ガード・invariant guard・否定形）の有効性の根拠として必須。behavior の failing アサーションについても、充足可能性チェックの仮実装に変異を当てて検出力を確認する
- **Phase 4（safety inspector）**: 独立した視点で実施する。tester が見落とした入力空間はここで見つかることが多い

### パターン

- **網羅性の証明**: 検証したい副作用を無条件に発生させる変異（例: スクリプト冒頭で stderr へ出力）を当て、失敗件数と起動回数の一致を確認する。「stderr 未検証の起動がゼロ」をアサーションの付け漏れなしに機械的に示せる
- **対称ガードの片側**: `a <= 上限` と `b <= 上限` のような対称なガードは、片側だけ回帰保護が抜けやすい。テスト内の値の分布（片方に `101` があるのにもう片方は `100` まで）を確認する

### 注意

- **等価変異**: 生存した変異がすべてテストギャップとは限らない。観測差が出ない変異（例: 子プロセスを起動しない処理で、子プロセスにしか影響しない設定を変更する）は等価変異として記録し、テスト追加の対象にしない
- **ファイル変更禁止との整合**: 検査中にプロダクションコードを変更できない場合は、スクラッチパッドへ一式を複製し、複製側で変異させる。ハーネスは対象パスを相対解決か環境変数で受ける設計にしておく

## 📊 テストカバレッジ

### カバレッジ目標

| 対象                 | 目標 | 理由                     |
| -------------------- | ---- | ------------------------ |
| **クリティカルパス** | 90%+ | 認証、決済、データ整合性 |
| **ビジネスロジック** | 80%+ | 重要な処理ロジック       |
| **ユーティリティ**   | 70%+ | 汎用関数                 |
| **UI/表示**          | 50%+ | 複雑でない表示ロジック   |

### カバレッジの解釈

- **高いカバレッジ ≠ 品質の保証**
- 重要なのは**意味のあるテスト**
- 分岐カバレッジ、条件カバレッジも考慮

## ⚠️ TDDのアンチパターン

### 避けるべきこと

1. **実装後にテストを書く** — TDDの利点（設計改善、仕様の明確化）が失われる
2. **一度に大きなテストを書く** — 小さく、インクリメンタルに進める
3. **テストの過剰な詳細化** — 実装の詳細ではなく、振る舞いをテスト
4. **モックの過剰使用** — 統合テストとのバランスを取る
5. **テストの重複** — 同じことを複数のテストで検証しない
6. **テストの偽装 passing** — `skip` / `todo` / assertion の緩和で無理やり通さない
7. **テストケース名にフェーズ・事象・誤情報を残す** — describe/it 名は「現在の仕様」として読める形を保つ。以下を避ける:
   - **TDD フェーズ語の混入**: `describe("〜（Phase 3b GREEN 実装対象）")`、`it("RED で書くテスト")` 等。GREEN 通過後は無意味になる
   - **事象ベース命名**: `describe("〜バグ")`、`it("issue #123 の修正")` 等、過去のバグ修正経緯を起点にした命名。振る舞い・仕様として書き直す
   - **assertion との乖離**: `it("7日分のデータが表示される")` と書きつつ 1 件しか assert しない等、名前が事実を表していない状態
8. **コメントに RED 時点の状況や修正前実装の解説を残す** — テストのコメントは「現在の仕様の補足」に限定する。以下を避ける:
   - **TDD フェーズ語を含むコメント**: `// Phase 3b GREEN 実装対象`、`// RED フェーズで失敗を確認` 等の戦略メモ
   - **「現状は…のため失敗する」系コメント**: RED 時点では正しいが GREEN 通過後は虚偽となる時限爆弾。最初から書かないか REFACTOR で削除
   - **修正前実装との比較コメント**: `// steppedEntries 方式では…だった` 等の過去の実装解説。履歴はコミットログで参照できる
   - 例外: AAA コメント（`// Arrange` / `// Act` / `// Assert`）等、プロジェクト標準として一貫採用されているものは保持

### 良いテストの特徴（FIRST原則）

- **F**ast（高速）: テストは素早く実行できる
- **I**ndependent（独立）: テスト間に依存関係がない
- **R**epeatable（反復可能）: 何度実行しても同じ結果
- **S**elf-validating（自己検証）: 成功/失敗が明確
- **T**imely（適時）: プロダクションコードの前に書く

## 🔧 Red-Green-Refactor 詳解（個別エージェント向け）

tester / implementer エージェントがテストケース単位で繰り返す手順:

1. **テストファイルの作成/編集（tester のみ）**
   - プロダクションコードより先にテストファイルを作成
   - ファイル命名はプロジェクトの既存パターンに従う

2. **失敗するテストを書く（RED / tester）**
   - 期待する振る舞いを assertion で記述
   - 1回のサイクルで書くのは最小単位のテスト1つ

3. **テストを実行して失敗を確認（tester）**
   - 実装対象アサーションが意図した assertion で failing していること（開始時 GREEN が正常な種別は「🧭 RED の種別」参照）
   - 構文エラー/インポートエラーによる失敗ではないこと（新規ファイル作成タスクを除く。対象が存在しない実行エラーは正常な RED だが、次の充足可能性チェックを経ないと意図した failing と区別できない）
   - **充足可能性チェック**: スクラッチパッドに対象コードの使い捨て仮実装を置き、全ケースが GREEN になることを確認する。外部プロセス・スタブ・カスタムハーネスを伴う RED で特に有効（ハーネス側のバグを検出した実例が複数ある）。**新規ファイル作成タスクでは必須**
     - 仮実装は**本来のパスに置かない**。理由は 3 点: tester がプロダクションコードを書く形になり役割境界を侵す、消し忘れると implementer の入力が汚染されて failing テストから実装を導く独立性が失われる、`rm` が拒否されるため新規ファイルの残骸がリポジトリ側に残る
     - ハーネスは対象パスを実行中のファイル自身の位置から相対解決するか、環境変数で受ける設計にし、複製側で実行できるようにする
     - 例外: ハーネスが本来のパスを固定していて複製できない場合、既存ファイルなら `git stash` / `git checkout` で確実に戻し、新規ファイルなら仮実装を作らず、充足可能性チェックを省略した旨とその理由をレポートに明記する
     - 使い捨てファイルの後始末は **`.discarded` サフィックスへのリネーム**で行う。`rm` は permissions.deny で拒否されるため試みない。スクラッチパッドはセッション終了時に破棄されるため蓄積は問題にならない
   - **ハーネス自身の検査**: リトライ／タイムアウトの枯渇は戻り値で検出しているか、サブプロセスで実行した部分の状態更新が呼び出し元に反映されない形になっていないか、環境変数がテスト対象まで伝播しているか、を確認する。ハーネスのバグはテストを黙って空振りさせる
   - 前提条件（特定ロケール・コマンドの可用性）を満たせないケースは黙って pass させず **SKIP として可視化**し、サマリに件数を出す
   - 開始時 GREEN のアサーションは「🧪 変異試験」で有効性を確認する
   - 実行ログを保存して implementer に引き継ぐ

4. **最小限の実装（GREEN / implementer）**
   - failing テストを通すだけの最小コードを書く
   - 将来の拡張や汎用化は考えない
   - **バグ修正時は同根の入力空間を洗い出す**: 指摘された入力だけでなく、同じ根本原因を共有する入力空間を列挙し、修正が各軸に有効かを確認する。例: 数値解釈の問題なら基数（8 進・16 進）・ロケール（文字クラスの照合順序）・符号・空白・オーバーフローの各軸。片側だけ塞いだ修正は次の検証で別軸から再不合格になる

5. **テストが通ることを確認（implementer）**
   - 該当テストだけでなく、既存テストも retrograde していないこと

6. **リファクタリング（REFACTOR / implementer）**
   - テストが通る状態を維持しながら改善
   - 重複除去・命名改善・既存パターンとの整合
   - **コメント・命名の浄化**（テストファイルから以下の残骸を除去する）:
     - describe/it 名の TDD フェーズ語（`Phase X` / `RED` / `GREEN` / `REFACTOR`）
     - 「現状は…失敗する」「未実装」「仮実装」等の RED 時点コメント
     - 戦略メモ（テスト直前のブロックコメントで実装方針を解説するもの）
     - バグフィックスの場合: 修正前実装との比較コメントを削除し、describe/it 名を「現在の仕様」として読める形にリネーム
   - ただし AAA コメント（`// Arrange` / `// Act` / `// Assert`）など、プロジェクト標準として一貫採用されているコメントは保持する
   - **実装意図のコメント**: 除去するのはフェーズ語と作業メモに限る。意図が自明でない実装（環境依存の回避・順序に意味がある処理・一見無関係な設定行）には、「何をしているか」ではなく「なぜそれが必要か」の理由コメントをプロダクションコード側に残す

7. **次のテストケースへ**
   - Step 1 に戻る

### フィードバックループでの再入場（implementer）

検証フェーズ不合格を受けて implementer が再入場する場合、初回の手順 4 からではなく以下で始める:

1. 受領済みのテスト（tester が回帰テストを追加している場合はそれも含む）を**自分で実行して RED を再現する**。指摘されたバグが実際に failing として現れることを確認してから着手する。この確認が漏れると「直したつもりが元から通っていた」「別の理由で通るようになった」を区別できない
2. 前回の実装判断のうち、指摘の原因となった箇所のみを見直す。無関係な箇所のリファクタリングは行わない
3. 手順 4 の「同根の入力空間の洗い出し」を行う
4. 修正後、RED 時点との比較（どの failing がどう解消したか）をレポートに含める

## 🔁 RED 中の仕様変更

RED フェーズの途中でユーザーから要件・期待値の変更が入った場合（動くものを見てから書式を変える等、実務では頻出する）:

1. **影響範囲を判定する**。どのテストファイルが影響を受けるかを特定し、影響を受けないファイルは変更せず、その理由を報告する
2. 期待値を新仕様に更新する
3. **充足可能性チェックと変異試験を新仕様で再実行する**。変更前の確認結果は無効になる

## 📝 テスト命名規約

### 基本形

- **TypeScript**: `describe('[対象]') > describe('[メソッド/機能]') > it('should [振る舞い] when [条件]')`
- **Python**: `class Test[対象]: def test_[メソッド]_[振る舞い]_when_[条件]`

### ポイント

- 「何をテストしているか」「どんな条件か」「期待される結果は何か」が名前から読める状態を目指す
- 実装関数名等をそのまま使うのではなく、**振る舞い**を記述する
