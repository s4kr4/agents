# 開発ワークフロー

エージェント間の責任範囲と開発フローを定義します。

## 原則

- **コーディングおよびそれに類する作業はエージェント経由で行うこと**
  - 調査・計画・実装・検証のいずれのフェーズも、自ら直接実行せず適切なエージェントに委任する
  - 対象: コードの新規実装・追加、バグ修正、リファクタリング、設定ファイルの変更、テストの作成・修正
  - 非対象（直接対応してよい）: 説明・解説・Q&A・ドキュメントの読み解きなど、ファイルへの書き込みを伴わない作業
- **使用するエージェントが不明な場合は、自己判断せずユーザーに確認する**
- **作業開始時にまず変更を分類し、フェーズ選択ガイド（後述）に従ってフェーズを決める**
  - フェーズの要否を分類と無関係に自己判断しない
  - 分類に迷う場合は、より重い分類を適用する

## Workflow Overview

### Phase 1: Investigation

**エージェント**: `@code-investigator`

- 既存コード構造の理解
- 関連ファイルの特定
- 影響範囲の分析
- 既存パターンの抽出

→ 調査完了後、Phase 2 へ

### Phase 2: Planning（Plan Mode）

**エージェント**: `@code-planner`
**条件**: 単純な変更はスキップ可

- 実装アプローチの設計
- タスクの分解と優先順位付け
- トレードオフの整理
- **想定入力範囲と不変条件の宣言**（信頼境界・想定する入力の軸と許容する集合・規模の上限・実行環境の前提・想定しない条件・判定の不変条件）
- ユーザー承認の取得

> **想定入力範囲の位置づけ**: 検証フェーズのブロック判定の範囲になる（`code-safety-inspector.md` の「判定範囲」）。記述形式は `code-planner.md` の Step 4.6、選べる軸は `/adversarial-testing` の「🎯 想定入力範囲の軸」を正本とする。
>
> **分類ごとの適用**: **複雑 / 中程度** は計画に宣言する。**単純 / UI表示バグ修正** は計画フェーズがないため、オーケストレーターが inspector への委譲時に範囲を示す（既定は「差分が持ち込んだ不具合と、前回指摘の塞ぎ漏れ」）。**軽微** は検証フェーズを実施しないため対象外。

→ 計画承認後、Phase 3 へ

### Phase 3: TDD Implementation（`/tdd` スキル駆動）

オーケストレーターは `/tdd` スキルを読み込み、以下のサブフェーズを実行する。

#### Phase 3a: RED（失敗テスト作成）

**エージェント**: `@tester`（ドメイン固有スキルは委譲時に指定）

- 完了条件から振る舞いを抽出
- テストファイル作成（プロダクションコードは書かない）
- 実装対象アサーションが failing であることを確認してレポート（種別ごとの件数を含む）

→ tester レポート受領後、Phase 3b へ

#### Phase 3b: GREEN / REFACTOR（実装）

**エージェント**: `@implementer`（ドメイン固有スキルは委譲時に指定）

- failing テストを最小実装で通す
- リファクタリング
- テスト不整合を検知した場合は Phase 3a に差し戻し（implementer はテストを編集しない）

→ 実装完了後、Phase 3.5 または Phase 4 へ

> **エージェントはドメインではなく役割で分ける**: tester / implementer の分離は CLI・スクリプト・ライブラリなど non-web の実装にも適用する。同一エージェントがテストと実装を書くと、fixture が「実装が想定する入力」に寄り、正規形から外れた入力（手編集ファイル・CRLF・タイムゾーン差）が検証されないまま通過した実例がある。分離は「検証の独立性」に属し、モデルの能力と無関係に価値が残る（`~/.agents/CLAUDE.md` の「フェーズの分類」参照）。ドメイン差はエージェントではなく委譲時に指定するスキルで吸収する（経緯は `plans/2026-09-06-role-based-agents.md`）。

### Phase 3.5: UI Verification

**エージェント**: `@web-ui-verifier`
**条件**: UI 実装を行った場合

- ブラウザでの視覚的確認
- インタラクション検証
- レスポンシブ確認
- アクセシビリティチェック

→ UI検証完了後、Phase 4 へ

### Phase 4: Verification & Quality Check

**エージェント**: `@code-safety-inspector`

- TypeScript型チェック
- ESLint/Prettier検証
- プロジェクト規約確認
- テストの実効性検証（変異試験）
- ブロック判定の範囲を承認済み計画の想定入力範囲に限定し、範囲外の発見を所見として分離
- 品質レポート作成
- コミット可否判定

→ 合格:
  - 「複雑」分類の場合は、コミット確認と併せて `/code-review ultra`（独立した複数エージェントによる並列敵対的検証）の実行をユーザーに提案する
  - それ以外の分類はそのままユーザーにコミット確認
→ 不合格: `@tester` / `@implementer` へフィードバック

> **なぜ「複雑」分類だけ提案するのか**: `@code-safety-inspector` は単一エージェントの逐次チェックであり、確証バイアス（自分が見た文脈をそのまま引きずって「確認」してしまう傾向）を完全には排除できない。`/code-review ultra` は文脈分離された複数エージェントが独立に反証を試みる構成のため、アーキテクチャ変更など影響範囲が大きい変更でこそ価値が出る。コスト・時間がかかりユーザー起動が必要なため、オーケストレーターから自動実行はせず提案にとどめる。判定はあくまで人間が行う。

## 責任範囲の原則

各タスクは担当エージェントちょうど1つに属する。詳細な担当領域・担当外は各エージェント定義（`~/.claude/agents/*.md`）の「責任範囲」を参照。担当エージェントが判断できない場合は、自己判断せずユーザーに確認する。

## Usage Examples

### 変更の分類

作業開始時に、変更を以下のいずれか1つに分類する。

| 分類           | 基準                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| 複雑           | 多ファイルにまたがる、またはアーキテクチャ変更を伴う                                                           |
| 中程度         | 複数ファイル、既存の明確なパターンに沿う                                                                       |
| 単純           | 1-2ファイルの小さな変更で、ロジックに触れる                                                                    |
| UI表示バグ修正 | 表示上の不具合の修正                                                                                           |
| 軽微           | ロジック（条件分岐・状態管理・データフロー・API・マークアップ構造・生成処理）に一切触れない 1-2ファイルの変更で、次のいずれかに限られるもの。(a) スタイル値（色・余白・フォント・クラス名等）・表示文言・コメント・ドキュメント文字列、(b) ビルド定義・設定ファイル中の値（Makefile のターゲット定義内のブランチ名・パス等、`.gitignore` の行の追加削除、`package.json` の `scripts` の値、CI 設定の値） |

分類に迷う場合（特に「軽微」か「単純」か）は、より重い分類を適用する。この規定は該当するかどうかを判断できない場合のものであり、「軽微」の定義に該当することが確かめられる変更は、対象がビルド定義・設定ファイルであっても「軽微」として扱う。

ビルド定義・設定ファイルの変更のうち、条件分岐・生成処理の追加や変更を伴うもの、新しいターゲット・スクリプト・ジョブの追加を伴うものは「軽微」に含めず、「単純」以上に分類する。

「軽微」に分類した変更は自動テストを作らない代わりに、次のいずれかで完了を確認する。

- dry run: `make -n <target>`、`npm run <script> --dry-run` 等を実行し、変更した値が展開後のコマンドへ反映されていることを確認する
- 集合の前後比較: 対象集合を決める設定（`.gitignore` 等）は、変更の前後で `git status --ignored` の件数と内容を比較し、意図した差分だけが生じていることを確認する
- 目視確認: 表示に関わる変更は `@web-ui-verifier` のスクリーンショットで確認する

### フェーズ選択ガイド

| 分類                                   | 調査 | 計画 | 実装（RED→GREEN） | UI検証（※） | 検証 | パターン |
| -------------------------------------- | ---- | ---- | ----------------- | ----------- | ---- | -------- |
| 複雑（多ファイル、アーキテクチャ変更） | ✅    | ✅    | ✅                 | ✅           | ✅（+ ultrareview提案） | 1        |
| 中程度（複数ファイル、明確なパターン） | ✅    | ✅    | ✅                 | ✅           | ✅    | 2        |
| 単純（1-2ファイル、ロジックあり）      | ✅    | ❌    | ✅                 | ✅           | ✅    | 3        |
| UI表示バグ修正                         | ✅    | ❌    | ✅    | ✅（Before/After） | ✅    | 5        |
| 軽微（スタイル・文言・コメント・設定値のみ） | ❌    | ❌    | 直接実装（テストなし。dry run・前後比較で確認） | ✅（目視のみ） | ❌    | 6        |

> **（※）UI検証**: UI 実装を行った場合は `@web-ui-verifier` を使用する。CLI・スクリプト・バックエンドのみの変更の場合はスキップする。

> **例外: 使い捨てスクリプト**
>
> 以下の条件をすべて満たす場合、ワークフローに従わず直接実装してよい：
> - バージョン管理しない（git 管理外）
> - 他のコードやチームメンバーが依存しない
> - 一度使ったら破棄する前提
>
> これ以外の「保守あり」スクリプトや「プロジェクトで使い続けるツール」は、通常のワークフローを適用すること。

**実装フェーズは変更の複雑さに関わらず常に実装エージェントに委任すること。**
自ら直接 Edit/Write でコードを実装することは禁止。

### 通常の開発パターン

> 「複雑」「中程度」分類では `@code-planner` の計画フェーズを挟む（フェーズ選択ガイド参照）。

#### パターン1: 完全な4フェーズ実行（複雑な変更）

```
@code-investigator でコードベース調査
   ↓
@code-planner で実装計画策定・承認
   ↓
@tester で failing テスト作成（RED）
   ↓
@implementer で実装（GREEN/REFACTOR）
   ↓
@web-ui-verifier でUI検証
   ↓
@code-safety-inspector で検証
   ↓
（合格時）ユーザーに /code-review ultra の実行を提案
```

#### パターン2: 計画フェーズ込み（中程度の変更）

```
@code-planner で計画策定（調査も含む）
   ↓
@tester で failing テスト作成（RED）
   ↓
@implementer で実装（GREEN/REFACTOR）
   ↓
@web-ui-verifier でUI検証
   ↓
@code-safety-inspector で検証
```

#### パターン3: 計画スキップ（単純な変更）

```
@code-investigator でコードベース調査
   ↓
@tester で failing テスト作成（RED）
   ↓
@implementer で実装（GREEN/REFACTOR）
   ↓
@code-safety-inspector で検証
```

> Web / CLI / スクリプト / ライブラリのいずれであってもこのパターンを使う。ドメイン固有スキル（`/py-implement` 等）は委譲時に指定する（`/tdd` の「スキル指定表」を参照）。

#### パターン5: UI表示バグ修正

```
@code-investigator でコードベース調査（/ui-debug スキル参照）
   ↓
@web-ui-verifier で現状のバグを再現・スクリーンショット取得（Before）
   ↓
@tester で failing テスト作成（RED。/ui-test を指定）
   ↓
@implementer で修正（GREEN/REFACTOR）
   ↓
@web-ui-verifier で修正確認（After）・Before との比較
   ↓
@code-safety-inspector で検証
```

> **通常パターンとの違い**: 実装前に `@web-ui-verifier` を使ってバグを「視覚的に証拠として記録」するフェーズが入る。これにより、バグの正確な再現条件を確認でき、修正後に Before/After で比較できる。

#### パターン6: 軽微変更（スタイル・文言・コメントのみ）

```
@implementer で直接修正（テスト作成なし）
   ↓
@web-ui-verifier で目視確認（スクリーンショット）
```

- 「変更の分類」で「軽微」に分類された変更に適用する。委譲プロンプトにパターン6であることを明示する
- UI表示に影響しない変更（コメント・非表示文字列のみ）の場合は `@web-ui-verifier` をスキップし、implementer 単独で完了する
- 修正中にロジックへの変更が必要と判明した場合は、その時点で「単純」以上に再分類し、対応するパターンに切り替える

### フィードバックループ（品質問題が見つかった場合）

`@code-safety-inspector` は `@tester` / `@implementer` との間でフィードバックループを形成します。
**最大3回のイテレーション**で問題を解消することを目指します。

**イテレーションカウントは呼び出し元（オーケストレーター）が管理します。**
`@code-safety-inspector` を呼び出す際は必ず現在のイテレーション番号を伝えてください（初回は1）。

~~~
@code-safety-inspector: 検査（イテレーション1）
   ↓ 不合格
@tester / @implementer へフィードバックレポート提出
   ↓
（指摘がテスト不足に起因する場合）@tester: 回帰テストを追加
   ↓
@implementer: 修正実装
   ↓
@code-safety-inspector: 検査（イテレーション2）
   ↓ 不合格
@tester / @implementer へフィードバックレポート提出
   ↓
（指摘がテスト不足に起因する場合）@tester: 回帰テストを追加
   ↓
@implementer: 修正実装
   ↓
@code-safety-inspector: 検査（イテレーション3）
   ↓
  合格 → コミット
  不合格 → ユーザーにエスカレーション（手動対応を求める）
~~~

> **テストを直すのは tester、実装を直すのは implementer**: 指摘が「ガードが未テスト」「入力空間に穴がある」などテスト側の不足に起因する場合は、`@tester` が回帰テストを追加してから `@implementer` が修正する。implementer はこのループの中でもテストファイルを編集しない。

**イテレーション上限に達した場合**は、以下を含むエスカレーションレポートを作成する：
- 残存する問題の一覧
- これまでの修正履歴のサマリー
- 手動対応の推奨事項

### 想定入力範囲の改訂

- `@code-safety-inspector` が「範囲外・重大」（宣言された環境・規模の内側で実害が出る範囲外の所見）を報告した場合、実装側の修正ループを続けず **Phase 2 に戻して想定入力範囲を改訂する**
- 改訂は `@code-planner` が行い、ユーザーの承認を得る
- 改訂後は Phase 3a（RED）から再開し、検証イテレーションを1から数え直す
- 改訂は**1タスクにつき1回まで**。2回目が必要になった時点でユーザーにエスカレーションする（範囲の見立て自体が成立していない）
- 範囲外・重大ではない範囲外の所見は改訂の対象にしない。コミット確認時にユーザーへ提示し、次回の課題とするかをユーザーが判断する

### アプローチ差し戻し（収束不能の検出）

- `@code-safety-inspector` は不合格時、各指摘に「**新規の根本原因**」か「**前回と同じ根本原因の別軸**」かの分類を付ける
- **同一の根本原因で2回連続して不合格**になった場合、実装側の修正ループを打ち切り、Phase 2 に戻して**防御の形式（アプローチ）そのもの**を変える
- 差し戻し先は `@code-planner`。ユーザーの承認を得てから Phase 3a（RED）で再開し、検証イテレーションは1から数え直す
- 「想定入力範囲の改訂」とは別の経路である。範囲の改訂は**範囲の外側**で実害が出るとき（起点は inspector の「範囲外・重大」）に発火し、アプローチ差し戻しは**範囲の内側**で同じ原因が塞ぎきれないとき（起点は同一根本原因での2回連続の不合格）に発火する。発火条件は重複しない
- アプローチ差し戻しは**1タスクにつき1回まで**。2回目が必要になった時点でユーザーにエスカレーションする

> **なぜ実装修正を続けないのか**: 列挙型の防御（ブラックリスト・状況依存の条件分岐）は、条件を1つ足すたびに穴が1つ開くため、指摘と修正が1対1で対応し続け、イテレーションを重ねても収束しない。収束させるには、正規化してからホワイトリストで判定する・危険が実を結ばない環境に封じ込める、といった**形式の変更**が要る。この判断は「failing テストを最小実装で通す」実装フェーズでは下せないため、計画フェーズへ戻す。

### tester ⇔ implementer 差し戻しループ

implementer がテスト自体の不整合（要件誤解・セットアップ不備）を検知した場合、自分で修正せずオーケストレーター経由で tester に差し戻す。

- 差し戻しは**同一テストにつき最大 2 回**
- 3 回目はユーザーにエスカレーション
- **implementer は絶対にテストファイルを編集しない**

### スキルフィードバックの記録（オーケストレーター）

以下のイベントが発生したら、オーケストレーターは直ちに `/skill-feedback` のオーケストレーターモードで、関連するスキルへのフィードバックを記録する：

- `@code-safety-inspector` の不合格判定
- tester ⇔ implementer の差し戻し
- サブエージェントへの再指示・訂正（1回のプロンプトで意図が伝わらなかった）
- イテレーション上限到達・エスカレーション
- ユーザーからの訂正・やり直し指示
- サブエージェントからの「スキルフィードバック」申告（レポート内）

> **見落とし厳禁**: 6番目のトリガー（サブエージェントからの「スキルフィードバック」申告）は、他の5つと異なりサブエージェント自身にファイルへ直接書き込む手段がない。そのため、レポートに申告が含まれていた場合は、他のイベント発生を待たず、レポート受領直後に即座に記録すること。記録を怠ると、そのフィードバックは完全に失われる。

記録方法・保存先は skill-feedback スキルの「オーケストレーターモード」を参照。関連するスキルが特定できない事象は記録しない。
